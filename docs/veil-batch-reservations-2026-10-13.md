# Veil: avoid searching unrelated messages for each surrogate

Source commit
[`e417aa1750c4352a1778ad23f3e09765bbb9021d`](https://github.com/antonsoo/veil/commit/e417aa1750c4352a1778ad23f3e09765bbb9021d)
was pushed to `main` and verified against the remote branch. All 18 changed
files, totaling 196,948 bytes, matched their pinned public raw URLs. The
[publication receipt](evidence/veil-batch-reservations-2026-10-13-public.json)
records sizes and SHA-256 values. Tags and `gh-pages` remained unchanged.
There was no PyPI release or hosted deployment; the version remains 0.4.4.

## Reproduced cost and change

Veil reserves source literals so restoring a placeholder cannot silently change
an example into someone's original data. That protection already worked, but a
batch of many short texts repeatedly searched all source records for every
candidate surrogate. A 4,000-message profile performed 32 million such checks;
reservation lookup consumed 5.59 of 6.33 profiled seconds.

The repair indexes normalized sources by the characters they contain. A
candidate searches only sources containing its first character. Most ordinary
text lacks the default placeholder delimiter. Sources arriving later inside an
SDK request update the same index, and the final integrity check still examines
all used replacements. Separate source boundaries and transaction rollback are
preserved.

```text
Candidate -> every source             -> plausible substring searches (before)
Candidate -> matching-character index -> substring searches (after)
                                      -> complete-batch verification
```

The [executable study](https://github.com/antonsoo/veil/blob/e417aa1750c4352a1778ad23f3e09765bbb9021d/studies/batch-reservations/README.md)
uses constructed inputs and fictitious identities. Medians below are from
three repetitions per case in fresh case processes, with all samples retained.
Before/after order alternates between cases. Python 3.12.12 ran on WSL2 with
14 available CPUs on a Ryzen 7 7800X3D. The timings exclude profiling overhead.

| Workload | Before | After |
| --- | ---: | ---: |
| 500 messages | 0.061 s | 0.027 s |
| 2,000 messages | 0.678 s | 0.121 s |
| 8,000 messages, 461,780 bytes | 9.866 s | 0.509 s |
| Same batch plus a literal placeholder | 8.909 s | 0.495 s |
| Same 8,000 messages joined into one text | 0.420 s | 0.431 s |
| 1,000 messages all containing the delimiter | 0.321 s | 0.205 s |
| 4,000 document blocks through the actual SDK | 2.784 s | 0.565 s |

Two additional controls use realistic email replacements and a custom template.
All nine cases preserve complete masked-output and vault hashes, plus exact and
tolerant round trips. The SDK case also preserves the serialized request hash.
It uses Anthropic 1.11.0 with a local mock HTTP transport; it does not measure
provider latency or establish live-service acceptance of the document. The
8,000-message case's whole-process peak RSS falls from 55,884 to 43,108 KiB.

## Verification

All 23 existing collision and CLI cases retain identical complete results,
including refused reused literals and rollback. All 36 actual SDK document
captures retain identical requests, answers and checks across sync/async and
buffered/streaming paths. The existing 240-document synthetic corpus preserves
all output and its 503 mappings. A direct substring reference, without a
character index, agrees on 20,000 deterministic availability checks with late
source additions, Unicode case folding, whitespace and reserved originals.

## Boundaries

When every source contains a candidate's first character, substring lookup
still scans every source. This is not a general linear-time guarantee. The
single-text control deliberately shows essentially unchanged speed. Source
references remain limited to the current batch. Detector accuracy and the
requirement to submit complete related raw texts are unchanged. These are
source/package checks, with no new hosted-browser or deployment claim.
